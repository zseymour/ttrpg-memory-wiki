# Campaign memory is a core-owned operation log projected into an editor-compatible vault

An independent local core owns the establishment-ordered operation log as the sole Authoritative record, stored in a dot-prefixed folder inside the campaign vault so a single folder carries the record, its projections, backup, sync, and export. Markdown pages are rebuildable Projection surfaces rendered for human reading — editor-compatible without depending on Obsidian, a plugin runtime, or any editor for correctness. Because file mutation cannot be prevented at any plugin or editor boundary, files are non-authoritative by design: Bypass edits are detected as divergence and compiled into attributed, proposed Memory operations instead of silently changing standing. Rejected alternatives: vault-native authoritative Markdown (silent mutation of history, no attribution, validation, or replay), a dedicated Obsidian plugin as host (couples the record to a vendor runtime without gaining multi-file atomicity), and files-as-record behind a "sole mediated writer" (unenforceable at the file boundary).

## Consequences

Every page, index, and embedding is a Derived view rebuildable from the log; only the log is authoritative, and Campaign export replays it without source re-extraction. Tools and agents submit operations through the core; file-diff intake is the fallback for unmediated human edits, with semantic preconditions taken from the edited projection's version so stale or offline edits conflict explicitly rather than overwrite. Mobile devices read fully via synced files and edit as deferred intake; no core runs there. Erasure compacts the log, re-projects pages, and purges core-owned indexes, converging across devices through ordinary file sync; sync-provider version history, OS backups, git history, and editor recovery snapshots are documented exclusions requiring setup guidance. Unrevealed material projects shielded by default as a rendering choice that never alters the record.
